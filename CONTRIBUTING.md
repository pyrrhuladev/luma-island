# Участие в Luma Island

Форки, pull request, вопросы и небольшие улучшения документации приветствуются. Начать можно с [Issues](https://github.com/pyrrhuladev/luma-island/issues): сообщить об ошибке, предложить функцию или задать вопрос через пустой issue.

Для крупной функции полезно сначала обсудить ожидаемое поведение в issue. Исправление опечатки или небольшой понятной ошибки можно сразу прислать в PR.

## Подготовка изменения

1. Создайте fork, склонируйте его и заведите отдельную ветку:

   ```powershell
   git switch -c fix/short-description
   ```

2. Внесите изменение с одной понятной целью. Для разработки нужны Windows и .NET 10 SDK.
3. Соберите проект и выполните проверки из корня репозитория:

   ```powershell
   powershell -File .\build.ps1
   powershell -File .\tools\Test.ps1
   ```

4. Отправьте ветку в свой fork и откройте PR в `pyrrhuladev/luma-island`. Опишите проблему, итоговое поведение и выполненные проверки. Если что-то проверить не удалось, укажите это прямо.

Для правки только текста достаточно проверить ссылки и форматирование. Для изменения поведения добавьте целевую проверку, если её можно воспроизвести автоматически.

## Что приложить к issue или PR

- **Ошибка:** версия Luma, версия Windows, шаги воспроизведения, ожидаемый и фактический результат. Для проблем с мониторами полезны масштаб интерфейса и число экранов; для FPS — наличие и версия FrameView SDK, если она известна.
- **Интерфейс:** снимки до и после, желательно для свёрнутой и раскрытой панели. Используйте демонстрационные названия треков и другие обезличенные данные. Укажите проверенные масштабы и экраны.
- **Производительность:** условия и длительность измерения, прогрев, включённые компоненты, состояние панели, версии и сравниваемые сценарии. Разделяйте расход процесса Luma и дополнительных процессов FrameView. Рабочий набор памяти и Private Bytes — разные показатели; сумму рабочих наборов нельзя считать уникально занятой памятью. Ориентир — [методика измерений](docs/performance.md).

## Границы изменений

Сохраняйте возможность отключать дополнительные источники данных. Новые функции не должны незаметно включать автозапуск, FPS или другой фоновый сбор. Подписки, таймеры и внешние сессии должны освобождаться при отключении соответствующего компонента. Для мини-графиков используйте существующие измерения.

В коммит не должны попадать:

- собранные EXE/DLL, ZIP-релизы, содержимое `artifacts/`, `.tools/`, `bin/`, `obj/` и `work/`;
- NVIDIA FrameView SDK, его DLL и другие сторонние бинарные файлы;
- личные настройки, журналы, диагностические выгрузки и данные из профиля Windows;
- персональные пути, имена пользователей, токены, адреса и скриншоты с личными данными.

Примеры конфигураций и тестовые данные создавайте отдельно, с вымышленным содержимым. Перед публикацией фрагмента журнала уберите личные данные и оставьте только относящийся к проблеме участок.

Код и ресурсы должны быть совместимы с [MIT-лицензией проекта](LICENSE). Для заимствованных материалов сохраняйте сведения об авторстве, источнике и лицензии. Соблюдайте [правила общения](CODE_OF_CONDUCT.md).

## Выпуск версии

Сопровождающий обновляет `Version` в обоих проектах `src/Luma.Island/Luma.Island.csproj` и `src/Luma.SensorHost/Luma.SensorHost.csproj`, `applicationVersion` в манифесте лицензий датчиков и `CHANGELOG.md`. При обновлении зависимостей проверяются их лицензии и исходники. После изменения исходного логотипа выполните `tools/Build-Icons.ps1` и проверьте значки в малых размерах. GitHub Actions проверяет PR и собирает portable-архив. После успешных проверок в `main` новая версия публикуется в Releases с тегом `v<Version>` и SHA-256. Уже опубликованные версии не перезаписываются; для исправлений выпускается следующая версия.
